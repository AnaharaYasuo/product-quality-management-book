# プロジェクト運用ルール & ガイドライン

本リポジトリ（`product-quality-management-book`）における変更管理およびリリース運用規約です。
Spec-Driven Development（SDD / 仕様・Issue駆動開発）の思想に基づき、すべての変更は追跡可能かつ段階的にリリースされます。

---

## 1. ブランチ戦略と役割

- **`production` ブランチ**:
  - **リリース専用ブランチ**（Amazon KDP出版・最終成果物の対象）。
  - `main` ブランチからのマージ（PR）のみ許可。直接コミット・直接プッシュは禁止。
  - ここにマージされると、KDP出版用の正式版EPUBが自動ビルドされます。

- **`main` ブランチ**:
  - 執筆・開発の統合ブランチ。
  - **直接コミット・直接プッシュは禁止**。
  - 各フィーチャー/章ブランチからのプルリクエスト（PR）経由でのみマージ可能。

- **作業ブランチ (`feat/*`, `fix/*`, `docs/*` など)**:
  - 変更内容を実装する個別ブランチ。

---

## 2. SDD（Issue駆動）執筆・変更フロー

すべての原稿執筆や構成変更は、まず **GitHub Issue** を起票してから開始します。

```text
[1. Issue作成] 仕様・執筆・修正内容の定義
      │
      ▼
[2. ブランチ作成] git checkout -b feat/issue-<No>-<title>
      │
      ▼
[3. 原稿執筆・修正]
      │
      ▼
[4. プルリクエスト (PR)] main ブランチ宛てにPRを作成 (Closes #<No>)
      │
      ▼
[5. main へのマージ] レビュー・プレビュー確認
      │
      ▼
[6. production へのPR & マージ] main -> production へマージして正式リリース
```

### ステップ詳細

1. **GitHub Issue の作成**
   - 変更の意図、執筆する章の要件、構成案などをIssueに明記します。
2. **作業ブランチの作成**
   - 例: `feat/issue-12-chapter2-metrics`
3. **コミット & プッシュ**
   - 変更をブランチにコミットしてPushします。
4. **`main` 宛てにプルリクエストを作成**
   - PRの概要に `Closes #12` などのIssue番号を紐付けます。
5. **`main` へのマージ**
   - `main` にマージされた段階で開発版EPUBがビルドされます。
6. **`production` へのリリースPR**
   - リリース単位（キリの良い章の完了や最終校正完了時など）で、`main` から `production` へのプルリクエストを作成してマージします。
   - `production` ブランチの最新EPUBがKDPへ入稿する正式成果物となります。
