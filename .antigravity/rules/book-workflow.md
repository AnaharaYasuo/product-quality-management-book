# プロダクト品質管理書籍プロジェクト 開発・執筆ルール

本リポジトリ（`product-quality-management-book`）はAmazon Kindle ダイレクト・パブリッシング（KDP）向け電子書籍の執筆プロジェクトです。
当プロジェクトにおいて、AIアシスタントおよび作業者は以下のルールを厳格に遵守すること。

---

## 1. ブランチ戦略とリリース規約

1. **`main` ブランチへの直接コミット・直接プッシュは絶対禁止**
   - 必ず作業ブランチ（`feat/*`, `fix/*`, `docs/*` 等）を作成して作業し、プルリクエスト（PR）経由でマージすること。
2. **`production` ブランチの役割**
   - **`production` ブランチこそがAmazon KDPへのリリース（出版）対象**。
   - `production` へのマージは **`main` ブランチからのみ** 許可される（直接コミット・プッシュ禁止）。
3. **成果物ビルドと版管理（GitHub Actions / Releases / Artifacts）**
   - **日常・検証（Artifacts）**:
     - `main` や作業ブランチへのプッシュ・PR時: 開発版プレビュー用EPUBが自動生成され、**GitHub Actions Artifacts** に一時保存される（レイアウト確認用・90日で自動失効）。
   - **正式入稿・重版（GitHub Releases）**:
     - **確定版の成果物は必ず Git タグ（`v*.*.*`）を打って GitHub Releases に永続保存する**。Artifactsは自動削除されるため、入稿成果物の保管場所として使用してはならない。
     - タグの付与により、GitHub Actionsが自動で GitHub Releases を作成し、入稿用EPUB（および必要に応じてPDF）をRelease Assetsとして添付する。

---

## 2. バージョニング規約（出版・版管理）

書籍の改訂・刷数管理は以下のセマンティックバージョニング形式に準拠する。

- **執筆・校正フェーズ（プレリリース）**:
  - `v0.1.0-alpha`: 初稿完成
  - `v0.9.0-rc.1`: 初校（入稿前チェック用）
  - `v0.9.1-rc.2`: 再校
- **正式出版フェーズ（本番リリース）**:
  - `v1.0.0`: **第1版 第1刷（初回販売・KDP初回入稿データ）**
  - `v1.0.1`: 軽微な誤字脱字修正、リンク切れ修正など（電書版のサイレントアップデート等）
  - `v1.1.0`: **第1版 第2刷（重版時・まとまった追記修正反映）**
  - `v2.0.0`: **第2版（構成の刷新・大規模な章追加）**

---

## 3. SDD（仕様・Issue駆動）開発・執筆フロー

原稿の執筆、構成案の変更、機能追加・修正はすべて **SDD（Spec-Driven Development）** の思想に基づき、GitHub Issueを起点とする。

1. **GitHub Issue 作成（仕様・要件定義）**
   - 執筆・変更を行う前に、必ずGitHub Issueを作成し、「執筆・変更の目的」「対象章や構成」「満たすべき品質要件」を記述する。
2. **作業ブランチの作成**
   - `feat/issue-<No>-<title>` などの形式でIssueに紐付くブランチを作成する。
3. **執筆・編集作業**
   - `manuscript/` 配下のMarkdownファイルおよび `metadata.yaml` などを編集。
4. **`main` 宛てプルリクエスト（PR）の作成**
   - 変更内容を説明し、`Closes #<Issue番号>` を記載してPRを作成する。
5. **`main` へのマージとAI編集者レビューの通過**
   - CIによる「LLM-as-a-Judge Editorial & UX Gate」等の品質チェックをすべてクリアして `main` へマージ。
6. **`production` への即時反映・マージ（★絶対遵守マストルール）**
   - **`main` へのマージで完了としてはならず、必ず `production` ブランチへのPR作成・マージまで一気通貫で完了すること**。
   - `production` への反映が完了して初めて作業完了（Done）とみなす。

## 4. 商業技術出版品質としての原稿基準（執筆規律）

各章の原稿執筆時は、以下の商業技術書水準（DoD）を必ず充足すること。

1. **コンテンツ密度とボリューム**:
   - 各章単体で **【8,000〜12,000文字】** の深掘りと具体度を担保する。薄い箇条書きや概要要約のみで終わらせることは厳禁。
2. **図解・ダイアグラムの必須化と構文確証**:
   - 各章に **Mermaid記法による概念図・アーキテクチャ図・フロー図を【最低2点以上】** 掲載する。
   - `subgraph ID ["表示名"]` のように全角文字・括弧・コロンを含むラベルは必ずダブルクォートで囲み、`python tools/validate_mermaid.py` による実ブラウザAST・SVG描画検証を100%パスすること。
3. **現場実践コード・プロンプト・設定例とAST構文確証**:
   - 読者が現場でコピペして即座に検証可能なコード・プロンプト・設定（YAML等）を **【最低2点以上】** 掲載する。
   - 掲載されるPython / JSON / YAML / TOMLコードはすべて `tools/lint_manuscript.py` のAST構文検査をパスし、コードブロックのネスト時は外側を4連バッククォート（```` ```` ````）とすること。
4. **アンチパターン（失敗事例）との対比**:
   - 理想論だけでなく、「現場でよくある失敗・形骸化パターン」と「その処方箋」を明確に対比する。
5. **QA合否判定基準（Pass/Fail Criteria）の明記**:
   - 何をもって合格・不合格（マージ不可、リリース不可）とするかの決定論的クライテリアを提示する。
6. **章末セルフワークショップ**:
   - 読者が翌日自チームで実践できるチェックシートまたは演習課題を章末に付与する。

## 5. 書籍のコア思想・アーキテクチャ原則

執筆にあたり、本書全体を通じて以下のコア原則を徹底すること。

1. **真のシフトレフト（全成果物の検証・レビュー・監査）**:
   - 「テストの前倒し」にとどまらず、企画（PRD）、UI/UXデザイン、機能仕様、アーキテクチャ、ソースコード、IaC、テスト資産、そして**「開発プロセス自体」**を含むすべての成果物を継続的に検証・監査する。
2. **AI前提（AI-native Assurance）**:
   - AIは単一の章で語るのではなく、要件定義からデプロイ監視・ポストモーテムまで**全工程の当たり前の前提（コパイロット/エージェント）**として組み込む。
3. **決定論的アンカー（Deterministic Anchors）**:
   - AIのハルシネーションや集団欺瞞を防ぐため、型・コンパイラ・静的解析・数学的テストといった「物理的・客観的フィルター」を必須の関所として配置する。
4. **プロセスの多様性とテスタビリティ**:
   - ウォーターフォール、スクラム、カンバン、Shape Up、トランクベース開発など、プロセスの類型に応じた品質保証の引き出しを提示する。
   - 人間の意識に頼るルールを排除し、機械的・決定論的に検証可能なガードレールを設計する。

---

## 6. 執筆環境と構成

- 原稿: `manuscript/` 配下のMarkdown（`.md`）ファイル
- スタイル: `manuscript/style.css`
- メタデータ: `manuscript/metadata.yaml`
- 画像: `images/`
- ビルドツール: GitHub Actions上のPandoc
